ReacherX is open source. You can fork it, run it on your own computer, and contribute changes back. This post takes you from zero to your first pull request, and shows you how to hand the whole setup to a coding agent.

You will need Node.js 22 or newer, pnpm 11, and accounts for the services in the area you work on. The code is available, but it does not come with free access to AI models or social platform providers.

## Fork first, then clone

You will not have push access to the main repository, so the standard open source flow starts with a fork. Fork `VecterAI/reacher-x` on GitHub, then clone your fork and keep the main repository as a second remote:

```bash title="Get ReacherX"
git clone https://github.com/YOUR-USERNAME/reacher-x.git
cd reacher-x
git remote add upstream https://github.com/VecterAI/reacher-x.git
git fetch upstream
git switch -c fix/short-description
```

Work on a branch, push it to your fork, and open a pull request against the main repository. That is the path every contribution here follows.

## Connect the services you need

Convex runs the backend. WorkOS handles sign-in. AI features need a model provider, and X/Twitter and LinkedIn features need their respective connections.

Some values belong in `.env.local`; others belong in your Convex deployment settings, set with `npx convex env set`. The [configuration guide](https://github.com/VecterAI/reacher-x/blob/main/docs/configuration.md) lists the right place for each. Don't commit your local settings or keys to Git.

Three services have special access rules:

- **SocialAPI** covers X search, hydration, and monitoring. It is invite only, so ask the maintainer for access.
- **Renidly**, formerly LinkdAPI, covers LinkedIn reads. Its signup requires a work email address.
- **Unipile** covers LinkedIn messaging and connected accounts, and uses standard signup.

Everything else follows the standard flow: Convex and WorkOS dashboards for the core, OpenRouter for models, Polar for billing, Resend for email.

## Start the app

Install dependencies and set up the backend once:

```bash title="Set up the backend"
corepack enable pnpm
pnpm install
cp .env.example .env.local
npx convex dev --once
```

Then leave the backend running in one terminal:

```bash title="Run the backend"
npx convex dev
```

In a second terminal, start the website:

```bash title="Run the website"
pnpm dev
```

Open the localhost address printed in the terminal, usually `http://localhost:3000`. For self-hosting only, the direct clone in the [README](https://github.com/VecterAI/reacher-x#self-hosting) is the right way.

## Hand the setup to a coding agent

Every step above is already written down for machines. The README shows a ready-made prompt, and [docs/development-setup.md](https://github.com/VecterAI/reacher-x/blob/main/docs/development-setup.md) is the full guide for humans and agents: the service table, dev versus production environments, an architecture diagram, and the recommended MCP servers and plugins, including the Convex MCP server and Vercel MCP.

Paste the prompt into Claude Code, Codex, Cursor, Antigravity, or any coding agent. It forks first, clones the right remote, creates a branch, fills only the variables your change needs, runs the checks, and prepares a clean pull request:

```text
Set up ReacherX for local development and open a pull request.

My change: <describe the fix or feature>

Read VISION.md first so the product vision is clear, then follow CONTRIBUTING.md, docs/development-setup.md, and agents.md. Summary:

1. Check before starting: search the open issues and pull requests at github.com/VecterAI/reacher-x for anything about my change. If an issue covers it, note the number and reference it in the PR. If an open PR already fixes it, stop and tell me. If nothing covers it and the change is bigger than a small fix, ask me whether to open an issue first.
2. Requirements: Node.js 22+ and pnpm 11. The repo pins pnpm via package.json, so run corepack enable pnpm.
3. I have no push access to VecterAI/reacher-x, so fork it on GitHub before cloning.
4. Clone my fork, add the upstream remote, and update main from upstream:
   git remote add upstream https://github.com/VecterAI/reacher-x.git
   git fetch upstream
5. Create a branch for one focused change: git switch -c fix/short-description
6. Install dependencies with pnpm install, then copy .env.example to .env.local.
7. Install agent tooling for this repo: the Convex plugin for Claude Code, Codex, or Cursor (or npx -y convex@latest mcp start), the Vercel MCP with vercel mcp, and npx convex ai-files install for repo AI files. The repo already ships Convex skills under skills/.
8. Read docs/configuration.md. Configure only the services for my change area and ask me for missing keys. Special cases: SocialAPI.me access comes from the maintainer, and Renidly signup needs a work email address.
9. Select a dev Convex deployment with npx convex dev --once. Set backend-only values with npx convex env set. Never commit .env.local and never upload it to Convex.
10. Run npx convex dev and pnpm dev in separate terminals. The site is at http://localhost:3000.
11. Before committing, run: pnpm exec tsc --noEmit, pnpm lint:strict, pnpm test:convex, and pnpm exec prettier --check on changed files.
12. Push to my fork and open a PR against VecterAI/reacher-x:main, referencing the issue from step 1 when there is one. For review bot comments (CodeRabbit), verify each suggestion before acting on it and ignore false positives with a short justification. Ask me before building anything bigger than a focused fix.
```

## Make one useful change

A confusing error message or a setup step that didn't work is a good first contribution. You don't have to begin with a large feature.

Read the [contribution guide](https://github.com/VecterAI/reacher-x/blob/main/CONTRIBUTING.md), look for an existing component or helper you can reuse, and test the behavior you change. For bigger ideas, talk to me before you start so we can agree on what to build.

Pull requests here are reviewed by bots as well as humans. CodeRabbit leaves comments on almost every PR. Verify each comment before acting on it: review bots produce false positives, so never apply a suggestion blindly. When a comment is wrong, say so briefly and move on. Fix only what is real, and let CI confirm the rest.

## Prefer to see it live first?

The README has a one-click deploy button. It copies the repository into your own GitHub account, creates a Vercel project, and prompts you for the listed settings. That copy is for running your own instance, not for contributing; contributing changes still starts with a fork. Your keys are still yours to add, so your copy can be running on Vercel and your own Convex deployment within minutes. The [setup guide](https://github.com/VecterAI/reacher-x/blob/main/docs/development-setup.md#deploy-your-own-instance) explains exactly what the button does and does not do.

If you want to work on the AI side, [the agent walkthrough](/blog/how-reacherx-agent-works) points to the main files. And if you're wondering why the whole application is open, [here's the story behind that decision](/blog/why-i-open-sourced-reacherx).
