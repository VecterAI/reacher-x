ReacherX can hold on to two kinds of memory. One kind starts with you. You tell the system to never send meeting requests, and it should obey. The other kind is inferred. The system watches work happen and tries to distill patterns worth repeating.

Those two kinds must not have equal authority. A pattern saying meeting requests sometimes got replies must never override your instruction to stop sending them. This post is about application memory. It is not about training model weights.

## Save an instruction the user asked for

[convex/agents/tools/rememberWorkspaceMemory.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/agents/tools/rememberWorkspaceMemory.ts) is the tool the agent calls when you say "remember this". It takes a stable memory key, an instruction kind, a summary, a scope, and optional channels. The memory key matters most for corrections. Reusing the same key updates or supersedes the earlier instruction instead of stacking a second one on the same topic.

Scope decides who the instruction applies to. A general workspace rule is different from a rule about one specific person, and a prospect-scoped memory gets linked to that person.

[convex/lib/workspaceMemoryScope.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/workspaceMemoryScope.ts) resolves which workspace a memory belongs to. It checks prospect threads first, then setup sessions, then workspace threads. Do not replace that with whichever workspace a query happens to return first. An instruction saved to the wrong workspace is a real bug, even when the instruction itself is sensible.

## Turn recorded work into possible lessons

Workflows record events as they run. A qualification finishes, a plan gets approved, a task fails, a prospect replies, a draft gets edited. [convex/workflows/memory.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/workflows/memory.ts) keeps one evaluation queue per workspace and treats abandoned runs as stale instead of forgetting them.

[convex/lib/learningCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/learningCore.ts) holds the distillation functions. They ask for reusable lessons about qualification, enrichment, outreach, and the operator's own notes. [convex/lib/memoryEvaluatorCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/memoryEvaluatorCore.ts) defines which event types the evaluator cares about and when a suggestion is promoted on its own:

```ts
return (
  args.confidence >= AUTO_PROMOTE_MEMORY_CONFIDENCE ||
  (args.confidence >= 0.72 && impactScore >= 0.85)
);
```

`AUTO_PROMOTE_MEMORY_CONFIDENCE` is `0.78` in this revision. These numbers are implementation thresholds. They are not measured probabilities that a lesson is true. When you judge a memory's quality, read the evaluation result and the events behind it.

Keep the records distinct in your head. An event, an evaluation run, a suggestion, and a promoted memory are four different things. Counting every recorded event as something the agent has learned will inflate every number you report.

## Retrieve with the right authority

[convex/lib/workspaceMemoryCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/workspaceMemoryCore.ts) is the center of the model. It tracks whether a memory is active, superseded, or disabled. It checks scope, surface, and channel before treating a memory as applicable, and it ranks what is left.

Operator instructions come first. Learned observations are advisory and must never override them. Retrieval is also bounded, so a prompt receives the applicable memories rather than everything the workspace has ever collected. When an embedding operation fails, the memory keeps its canonical instruction and its indexing state records the failure, so a retry can pick the work up later.

That split helps when you debug. "The instruction exists" and "the operation that needed it received it" are two different claims. Check both.

## Test behavior, not storage

A useful test saves an instruction, asks for later work in the same workspace, and checks the context that the operation actually received. Then add a second workspace and confirm the instruction did not cross over. A correction, a disabled memory, and a failed indexing attempt are worth covering too.

Start from the existing coverage.

- [convex/workspaceMemory.integration.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/workspaceMemory.integration.test.ts) saves instructions and builds workspace context.
- [convex/workspaceMemoryIndexRetry.integration.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/workspaceMemoryIndexRetry.integration.test.ts) retries failed indexing with backoff.
- [convex/memoryEvaluationQueue.integration.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/memoryEvaluationQueue.integration.test.ts) keeps each workspace's evaluation queue in order.

Feedback can change later work. That does not guarantee steadily improving outcomes, and it never makes an inferred lesson true. The [memory guide](/blog/teach-reacherx-what-you-want) explains how to steer it as a user, and [Agent observability](/blog/understand-agent-observability) shows the records that let you check what happened.
