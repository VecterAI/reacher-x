Outreach takes longer than a web request. A plan can wait days for a prospect's next post, pause until you approve a message, or change course after a reply arrives. If any of that lived only in the browser, closing a tab would lose it.

The work also has to be careful about retries. A failed request might mean the message never went out. It might also mean the provider accepted it and the confirmation was lost. Sending again after the second case would post the same reply twice.

## How a plan runs

[convex/workflows/outreach.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/workflows/outreach.ts) defines `outreachPlanWorkflow`. It runs one approved plan, task by task. The task types are `comment`, `react`, `dm`, `wait`, and `ask_human`.

Before anything runs, the workflow checks the plan state:

```ts
if (plan.status !== "approved") {
  return {
    success: false,
    status: "skipped",
    error: `Plan is not ready for execution (status: ${plan.status})`,
  };
}
```

Approval is a property of saved data, not of whoever happens to have the page open. The workflow also compares execution generations, so a plan that was replaced while work was in flight exits instead of racing the newer version.

Comment, reaction, and DM tasks each run through an action step in [convex/outreachActions.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/outreachActions.ts), which rechecks that the plan and task are still current before touching a provider. When one of those actions fails, the workflow pauses the plan, or blocks it when the account needs reconnection, and tells you why.

## Waiting without losing your place

A `wait` task comes in two shapes. A timed wait simply resumes after its delay. A "next post" wait creates a monitor for the prospect and then waits for that event. An `ask_human` task posts a notification and waits the same way:

```ts
await step.awaitEvent({
  name: `human_response:${task._id}`,
});
```

That event lives in persisted workflow state, not in a browser promise that a refresh would destroy. Turning on autonomous outreach does not remove these waits either. The workspace setting defaults to review required, and even an autonomous workspace still waits for a prospect's next post or a human answer.

Where a task needs review, the approval request is durable too. The task stores an approval event id along with the context for the message and the source post, so the right panel can reopen later. Approving sends that stored event rather than trusting whatever the current page remembers.

## When a reply changes the plan

[convex/workflows/adaptiveOutreach.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/workflows/adaptiveOutreach.ts) handles recorded interaction events. The workflow claims the event, generates a decision, and applies it. The decision can continue the plan, complete it, or abandon it, and continuing restarts the outreach workflow.

Applying a decision can also be rejected. If a newer plan version or a newer interaction has already superseded the event, the result comes back as superseded instead of applied. That check keeps an old reply from overwriting a decision made later.

This is the concrete meaning of "self-driving" in ReacherX. The system can react to new interactions and choose the next piece of work. It does not mean the agent can ignore workspace instructions or skip approval boundaries.

## What to check when something goes wrong

Keep the records separate when you report a bug. The prospect, the plan, the task, the workflow run, the interaction event, and the provider result each answer a different question.

[convex/lib/outreachExecutionCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/outreachExecutionCore.ts) holds the check that decides whether an execution attempt is still current. A UI card that says a task was approved is not proof the platform sent anything. For provider-side truth, look at the execution records and the recovery rules exercised in [convex/outreachRecovery.integration.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/outreachRecovery.integration.test.ts). [convex/lib/outreachExecutionCore.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/outreachExecutionCore.test.ts) covers the currency check, and [convex/outreachPanelContext.integration.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/outreachPanelContext.integration.test.ts) covers the approval panel context. The regressions there include double approval, stale events, a retry after a partial send, and a plan that changed while work was waiting.

For manual verification, use a controlled test conversation and confirm the result on the platform itself. A test of message formatting alone cannot prove that a send happened.
