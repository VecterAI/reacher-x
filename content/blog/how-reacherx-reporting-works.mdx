Every number on a dashboard has a history. Something happened, the app recorded it, reporting code grouped the record into a time window, and the interface gave the result a label. If any layer disagrees with the others, the chart can look perfectly healthy while saying the wrong thing.

That risk is why the reporting path is worth understanding before you add a metric to it.

## Two dashboards count different things

[features/analytics/ui/AnalyticsDashboard.tsx](https://github.com/VecterAI/reacher-x/blob/main/features/analytics/ui/AnalyticsDashboard.tsx) is the outcome view. It reports new people found, response rate, pending approvals, outreach issues such as paused plans and failed tasks, and processing states.

[features/agent-ops/ui/AgentOpsDashboard.tsx](https://github.com/VecterAI/reacher-x/blob/main/features/agent-ops/ui/AgentOpsDashboard.tsx) is the agent operations view. Its tabs cover overview, discovery, quality, memory, and activity, and its detail views let you open individual queries, memories, events, evaluator runs, and suggestions.

The two are related, not interchangeable. A memory event is not a new prospect. A generated query is not an activated query. When you add a metric, keep the original meaning intact instead of reusing whichever count is convenient.

## Follow one number through the backend

[convex/analytics.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/analytics.ts) assembles the dashboard, and [convex/lib/analyticsCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/analyticsCore.ts) holds the shared calculations. The response rate comes from recorded contacted and responded events inside the chosen window:

```ts
currentValue: calculateRate(respondedCurrent, contactedCurrent),
```

Read the numerator and the denominator before you change the label above that line. The rate is an event-window calculation. It is not a cohort study that follows the same contacted people until every possible reply has arrived, so describe it that way to users.

Daily rows back the windowed reads.

## Readiness and time both matter

The frontend asks [convex/workspaceReporting.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/workspaceReporting.ts) whether reporting is ready. When it is, the dashboards use reactive queries that stay live. When it is not, they fall back to snapshot actions instead of showing zeros, because an empty result is not proof that nothing happened.

Time windows follow the workspace's reporting time zone. Event timestamps are stored in UTC, which keeps ordering and hour buckets consistent across the system, while the reporting time zone decides which day the dashboard calls today. If a count changes oddly around midnight, compare the visible range with the normalized backend window.

Labels adapt to the workspace use case. A recruiting workspace can read candidates where the stored record is still a prospect. Presentation names and data meanings have to stay separate.

## Make the detail view explain the summary

[features/agent-ops/ui/AgentOpsPanel.tsx](https://github.com/VecterAI/reacher-x/blob/main/features/agent-ops/ui/AgentOpsPanel.tsx) opens the records behind the numbers. A memory detail can show its source, confidence, canonical instruction, status, and indexing state. An evaluator run can show what it produced. Moving from "something happened" to the record that explains it is the whole point of this view.

New summary metrics need a clear definition and a sensible investigation path. Start from [convex/agentOpsDashboard.integration.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/agentOpsDashboard.integration.test.ts), [convex/agentOpsInventory.integration.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/agentOpsInventory.integration.test.ts), and [convex/workspaceReportingAggregate.integration.test.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/workspaceReportingAggregate.integration.test.ts). Cover empty data, time boundaries, repeated events, paging, and a workspace whose reporting is not ready yet.

Before you contribute a chart, write down exactly what one count means, prove it with a small fixture, and inspect the rendered label. The [contributor guide](/blog/help-build-reacherx) explains how to turn that change into a useful contribution.
