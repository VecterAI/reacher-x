After finding someone relevant, ReacherX needs enough information to explain who they are and help you approach them. Enrichment turns available social data and supporting posts into a fuller profile.

It is not a promise to find every email address, phone number, or personal detail. Missing information and partial results are part of the data model, and an empty field is often more accurate than a plausible guess.

## The two main layers

Start with [convex/workflows/enrichment.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/workflows/enrichment.ts). The `enrichmentWorkflow` checks the prospect, the workspace, and the workflow state, then chooses the platform-specific path.

The shared extraction logic lives in [convex/lib/enrichmentCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/enrichmentCore.ts). The workflow runs internal actions such as `runTwitterEnrichmentCore` and `runLinkedInEnrichmentCore`, so the core executes in the Node.js environment those APIs need.

Keep that split when you contribute. Fetching, scheduling, and saving belong to the orchestration path. Reusable interpretation and normalization belong in the core, not copied into every agent tool that asks to enrich someone.

## Preserve evidence while shaping the profile

The core result carries fields like a short introduction, title, company, website, location, social links, and pain points backed by posts. Contact fields remember where they came from. Finance-related details, when present, carry their evidence posts too.

Everything the profile shows should be something the available information supports. The UI can then show the source post behind a claim instead of a bare assertion.

The core makes partial completion explicit in its type:

```ts
enrichmentStatus: "enriched" | "partial" | "failed";
```

The workflow return type adds one more state, `pending`, for the case where the run was skipped. An archived person, for example, keeps their stored status instead of starting a new run.

Evidence posts get their own helper. `convertToEvidencePosts` produces a consistent record with an ID, text, URL, platform, and an optional original provider payload. The UI shows the source post, while other parts of the system use the smaller, consistent representation. `deduplicateEvidencePosts` keeps repeats from piling up.

## Links and contact details are their own problem

Profile websites may be shortened URLs or separate display text. The enrichment code uses shared URL helpers and Twitter profile-link resolution rather than trusting any string the model returns.

Public contact discovery runs through [convex/lib/contactDiscoveryCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/contactDiscoveryCore.ts). Read that path before changing how email or phone fields are filled. Where a contact detail came from matters as much as the fact that it exists.

If you are fixing a profile link, preserve the difference between the destination URL and the text shown to a reader. If you are fixing missing evidence, follow the post conversion and deduplication path before touching the prompt.

## Pass useful context to the next job

After enrichment is saved, the workflow indexes relevant context for retrieval and records a memory event. It can then trigger automatic plan generation when the person is eligible and the current state allows it.

Not every enrichment call creates a new plan. There are setup-preview paths, state checks, and existing-plan checks. A retry should never turn into a duplicate active plan.

To investigate a bug, keep a small redacted provider response and the expected normalized result side by side. Check both a complete response and one with optional fields missing. Then confirm the profile shows the source correctly and that planning handles the partial information.

The next article explains [how outreach plans are prepared](/blog/how-reacherx-planning-works). The distinction matters: enrichment says what is known about someone, and planning decides what to do about it.
