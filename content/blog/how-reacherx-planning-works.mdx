An outreach plan is more than a generated message. It describes a sequence of actions for one person, built from the workspace's goal and what the system already knows about that person.

The hard part is making those actions refer to real people, real posts, and channels that actually exist. A convincing plan that targets the wrong post is still wrong.

## Read the plan inputs before the prompt

Start with [convex/lib/autoPlanCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/autoPlanCore.ts). The `AutoPlanGroundingContext` type describes the information used for automatic planning. Nearby helpers build research queries, decide whether there is enough grounding to proceed, and validate the resulting draft.

Grounding means the plan can point at real information. The system should not invent a social post or assume a messaging channel exists just because that would make a neat plan.

Three functions do the work. `buildGroundedAutoPlanPrompt` produces the model-facing prompt, `parseAutoPlanTransportDraft` reads the transport answer, and `validateAutoPlanDraftAgainstGrounding` checks the draft against the context. Valid JSON is only one check. The actions also need to fit the facts.

## Save a plan through shared rules

[convex/lib/outreachCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/outreachCore.ts) owns `createOutreachPlan`. Before writing anything it confirms the prospect belongs to the supplied workspace and user, verifies outreach eligibility, checks for an existing active plan, and validates task inputs.

One state choice in that function decides how much approval the plan needs:

```ts
const initialPlanStatus =
  (agentSettings?.autonomyMode ?? DEFAULT_WORKSPACE_AGENT_AUTONOMY_MODE) ===
    "autonomous" && accountReadiness.missingPlatforms.length === 0
    ? "approved"
    : "draft";
```

Review-required is the default. An autonomous workspace skips the review, but only when every account platform is ready. A missing platform forces a draft.

The single-active-plan rule also matters when two operations run close together. Updating an existing plan and creating another plan are different operations. Never solve a duplicate-plan error by bypassing the check.

## Selected people and instructions stay separate

The user-selected batch path starts at [convex/agents/tools/planBatch.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/agents/tools/planBatch.ts) and continues into [convex/lib/planBatchCore.ts](https://github.com/VecterAI/reacher-x/blob/main/convex/lib/planBatchCore.ts). A user can give a shared instruction and a different instruction for each selected person.

The selections need real application IDs and workspace validation. A model-generated string that looks like a database ID is not a valid selection. Trace the selection context and the batch records rather than trusting names in the generated answer.

A batch can also end with mixed outcomes. One person may already have a plan while another is ready for a new one. The UI should explain those results individually. Reporting a batch as failed when some work succeeded is not honest enough.

## Test the boundary that could send the wrong thing

Useful tests include a fabricated post reference, an unavailable channel, a duplicate plan, a stale batch result, and instructions crossing between selected people. The repository's `tests/plan-batch-core.test.ts` and `tests/agent-thread-target-selection.test.ts` cover parts of that path.

If you need the controls before the code, read the [batch-planning flow](/blog/create-plans-for-several-people) first. Then follow [outreach execution](/blog/how-reacherx-outreach-runs) to see how an approved plan becomes durable work, waits for events, and reacts to replies.
