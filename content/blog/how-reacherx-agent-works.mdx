Pick one person shown in the app and ask how they got there.

Who searched for them? Why were they considered a match? Where did the details on their profile come from? Answering those three questions takes you through the entire system, and it is a much better first trip through the code than reading every file.

## Follow a person from search to conversation

A workspace describes who you are looking for. Discovery turns that description into searches on X/Twitter and LinkedIn, and saves the people it finds. Qualification checks each person's evidence against the workspace requirements. Enrichment builds a fuller profile for the people who pass. Planning works out how to approach someone. Outreach runs the plan, including waits, approvals, and responses to incoming replies.

```text
workspace -> discovery -> qualification -> enrichment -> planning -> outreach
```

That is the normal path, but not everyone follows it. You can add a person by hand, or a setup preview can create one while you are still setting up the workspace. Records carry a `discoverySource` field that tells you how someone arrived, and manual entries may not have one. Check it before you try to follow anything backwards.

One more thing you will see everywhere: events. Every meaningful step records one. Some events feed Analytics and Agent observability. Some become input for memory, which saves lessons the agent can use later.

## Where the code lives

ReacherX is a Next.js and React app with Convex for backend functions and data. Keep this map open while you read:

| Location                                      | What belongs here                                                  |
| --------------------------------------------- | ------------------------------------------------------------------ |
| `app/`                                        | Next.js routes and page composition                                |
| `features/`                                   | Feature-specific interfaces, hooks, and supporting code            |
| `shared/`                                     | Components and utilities used across features                      |
| `convex/agents/tools/`                        | Tool inputs, context resolution, and calls to shared operations    |
| `convex/workflows/`                           | Multi-step orchestration, waits, retries, and state checks         |
| `convex/lib/`                                 | Shared business rules, normalization, scoring, and context helpers |
| `convex/schema.ts` and `convex/validators.ts` | Stored data shape and shared validators                            |

Here is the pattern in one example. An agent tool can ask to qualify someone, but the qualification rules do not live in the tool. The tool calls a workflow, and the workflow calls shared core functions. If another caller needs the same behavior, the fix belongs in the core, not in the tool.

Before you add a helper, search for an existing one. The project already has shared time utilities and validators for most of this, and the links in these walkthroughs point at the current main branch so they stay fresh as the code moves.

## Pick the part you want to understand

Each walkthrough follows the same shape. It explains what the step does, shows where it lives, and leaves you with something specific to check.

- Strange search result? Start with [discovery](/blog/how-reacherx-discovery-works), then follow it into [qualification](/blog/how-reacherx-qualification-works).
- Missing or incorrect profile detail? Read [enrichment](/blog/how-reacherx-enrichment-works).
- Plan or message you didn't expect? Read [planning](/blog/how-reacherx-planning-works) and [outreach execution](/blog/how-reacherx-outreach-runs).
- Instruction the agent seems to remember? Follow [memory](/blog/how-reacherx-memory-works).
- Dashboard number you can't explain? Read [reporting](/blog/how-reacherx-reporting-works).

Keep the workspace ID in view as you trace a record. When you are checking whether a message actually sent, follow the saved task state and the provider result. A generated draft alone won't tell you that.

You don't need to understand the whole application before your first contribution. [Run it locally](/blog/run-reacherx-yourself), reproduce one problem, and follow the relevant path. If you get stuck, ask in [Discord](https://discord.gg/BQttyr8jY). Questions help me see where the explanation is missing.
